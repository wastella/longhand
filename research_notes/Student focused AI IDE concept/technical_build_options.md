# Technical build options for a minimal, student-focused, AI-tutor code editor (as of 26 November 2026)

Scope note for the report writer: research was done on 2026-11-26 with about 23 search/fetch calls. Claims under "Cited Findings" come from pages fetched or search results returned in this session; where a claim rests on a search-result summary rather than a full page read, it is marked "(search summary)". Things I know only from background knowledge and did not re-verify are placed under Inferences or Gaps and labelled as such. Several sub-questions in the brief (DAP/debugpy, Jupyter kernel protocol, remote-SSH implementations, Tauri PTY plugins, Lapce/Pulsar effort, Theia AI, Kiro, Windsurf) returned no usable sources in the time available; they are listed as gaps rather than filled in.

## 1. VS Code extension: what it can and cannot do

### Takeaway
An extension is still the cheapest way to get a tutor into a full-featured Python editor, but the AI extension surface changed materially in 2026: the Chat Participant API is now deprecated, the "Local harness" it runs on is scheduled for removal in February 2027, and Microsoft's recommended path is "agent plugins" (skills + MCP server + optional custom agent) plus Language Model Tools. A tutor that owns its own webview panel and calls the Claude API directly is the design least exposed to that churn; it can turn off built-in AI with one setting but cannot remove or restyle the workbench.

### Cited Findings
- The VS Code AI extensibility overview (page dated 11/25/2026) lists five options: agent plugin (packages skills, an MCP server, and optionally a custom agent; MCP Apps can add interactive controls in chat), language model tool (runs in the extension host with access to VS Code extension APIs, extends agent mode), MCP tool (runs outside VS Code, no access to extension APIs), chat participant (deprecated), and the Language Model API (direct programmatic model access for features such as code actions or custom views). — [VS Code AI extensibility overview](https://code.visualstudio.com/api/extension-guides/ai/ai-extensibility-overview)
- "Chat participants are deprecated and are not supported in the Copilot harness." The API "remains available for Local harness compatibility. Do not use it for new Copilot integrations." There is no automatic conversion of existing participants' request handlers, history, or UI. — [Chat Participant API guide](https://code.visualstudio.com/api/extension-guides/ai/chat)
- A site banner states: "The Local harness is deprecated and will be removed in February 2027." No separate removal date is given for the Chat Participant API itself. — [Chat Participant API guide](https://code.visualstudio.com/api/extension-guides/ai/chat)
- Agent plugins "are the recommended replacement for deprecated chat participants" and "do not require a participant request handler"; for capabilities that depend on editor APIs or live editor state, the docs recommend extension (language model) tools. — [VS Code AI extensibility overview](https://code.visualstudio.com/api/extension-guides/ai/ai-extensibility-overview)
- Custom agents are a built-in user-facing feature: VS Code 1.110 (February 2026 release) says that if you want your own version of ask mode you can "create a custom agent that matches your needs by defining its tools, prompt, and language model" (search summary). — [VS Code 1.110 release notes](https://code.visualstudio.com/updates/v1_110)
- A May 2026 GitHub changelog notes that custom agents, skills, and instructions can be drafted from a natural-language description (search summary). — [GitHub changelog, April releases](https://github.blog/changelog/2026-05-06-github-copilot-in-visual-studio-code-april-releases/)
- `chat.disableAIFeatures` disables and hides built-in AI features, including chat and inline suggestions, and disables the Copilot extensions; it can be set per workspace or per user (search summary of official docs). — [VS Code AI settings reference](https://code.visualstudio.com/docs/agents/reference/ai-settings); [Set up GitHub Copilot in VS Code](https://code.visualstudio.com/docs/setup/copilot)
- Narrower controls exist: `github.copilot.enable` (a per-language map) for inline suggestions and `github.copilot.nextEditSuggestions.enabled` for next-edit suggestions (search summary). — [VS Code AI settings reference](https://code.visualstudio.com/docs/agents/reference/ai-settings)
- At least one university course already publishes a guide to disabling AI-assisted coding in VS Code for students, which shows the settings-based approach is in real classroom use (search result title only; page not read). — [Harvey Mudd CS 133 guide](https://www.cs.hmc.edu/~beth/courses/cs133/lab/guides/vscode/index.html)
- Forks resolve extensions through Open VSX or their own registries, not the Microsoft Marketplace; Cursor uses Open VSX plus its own infrastructure (search summary). — [Cursor forum: Pylance licensing thread](https://forum.cursor.com/t/pylance-in-cursor-special-license-or-intentional-inducement-of-copyright-infringement/27794)
- A March 2026 EclipseSource article reviews domain-specific AI extensions in VS Code and argues they are "worth another look" (title and existence only; not read). — [EclipseSource, 19 March 2026](https://eclipsesource.com/blogs/2026/03/19/domain-specific-ai-extensions-vs-code/)

### Inferences
- Because chat participants are tied to a harness being removed in February 2027, building the tutor as an `@tutor` chat participant today means a forced rewrite within roughly three months of this report. The two durable shapes are (a) an agent plugin (skills + MCP server + custom agent) that runs inside Copilot's chat, or (b) an extension-owned webview panel that talks to the Claude API itself.
- Shape (a) puts the tutor inside Copilot's agent harness, whose default purpose is to write code. Tutor guardrails then depend on a custom agent's prompt and tool list inside someone else's harness, and the student is one mode-switch away from normal agent mode. Shape (b) keeps the guardrails in code the builder controls and lets `chat.disableAIFeatures` hide everything else. For a "does not write the code for me" product, (b) fits better.
- Shape (b) also ports best to forks (Cursor, Windsurf, VSCodium), because it uses only long-stable APIs (webviews, diagnostics, CodeLens, decorations, terminals) rather than Copilot-specific ones. This is an inference; I did not test or find documentation on Language Model API availability in forks.
- An extension can set configuration values (including `chat.disableAIFeatures`) at workspace or user scope, so "suppress other AI" is achievable by default. It is not enforceable: the student can flip the setting back. For a self-directed student that is acceptable; it is a commitment device, not a lock.
- From background knowledge, not re-verified this session: the stable extension API includes webview views/panels, text editor decorations, CodeLens, `languages.onDidChangeDiagnostics`/`getDiagnostics`, the Testing API (test runs and results are observable by the extension that owns the test controller; reading results from another extension's controller, such as the Python extension's pytest runs, has historically been limited), terminal shell integration (command start/end events and exit codes), and the Notebook API. Extensions cannot remove core workbench UI or restyle it beyond themes and contributed views; "simplifying" VS Code is done with settings, a profile, and Zen mode, not by an extension. Treat these as needing a check against the current API reference before design is frozen.

### Gaps
- Whether the Language Model API (`vscode.lm`) requires GitHub Copilot sign-in or a subscription, and whether an extension can register its own model provider (the docs navigation lists a "Language Model Chat Provider" guide, which I did not read). — not stated on the pages fetched.
- What "Copilot harness" and "Local harness" precisely are; the fetched pages use the terms without defining them.
- Profiles: I found no source this session on shipping a preconfigured profile with an extension or as a profile template, nor on how `chat.disableAIFeatures` behaves inside a profile.
- No source read on the current state of the Testing API's cross-extension result access, the terminal shell integration API, CodeLens, or the Notebook API; no proposed/unstable API list was checked.
- Whether agent plugins, language model tools, or the Language Model API function at all in Cursor, Windsurf, or VSCodium.

## 2. VS Code fork or Code-OSS distribution

### Takeaway
Forking buys full control of the workbench (the one thing an extension cannot have) at the price of a permanent merge treadmill and loss of Microsoft's proprietary extensions, including Pylance. Even funded teams treat this as a serious cost, and the one small open-source AI fork I checked (Void) paused development; for a part-time solo student this is the wrong starting point.

### Cited Findings
- EclipseSource's analysis of forking: fork changes accumulate, and "maintaining compatibility with the rapidly evolving VS Code codebase becomes increasingly challenging"; divergence looks safe early and the maintainer carries all compatibility work alone (search summary). — [EclipseSource, "Is Forking VS Code a Good Idea?", Dec 2024](https://eclipsesource.com/blogs/2024/12/17/is-it-a-good-idea-to-fork-vs-code/)
- An Eclipse Foundation post makes the same point: maintaining a fork is "a significant burden" because VS Code is under active development and evolves rapidly (search summary; note the author's affiliation with Eclipse Theia, a competing base). — [Eclipse blog, "Why Cursor, Windsurf and co fork VS Code, but shouldn't"](https://blogs.eclipse.org/post/thomas-froment/why-cursor-windsurf-and-co-fork-vs-code-shouldnt)
- Positron (Posit's data-science fork) documents a layered upstream-merge workflow and a rule of keeping its own changes small: its goal is to extend Code OSS, overriding upstream code "only in a few places"; on conflicts it accepts upstream and reapplies Positron changes (search summary of a mirror of Positron's repo docs, not the primary repo). — [Positron merge-upstream skill, mirrored](https://tessl.io/registry/skills/github/posit-dev/positron/merge-upstream-vscode)
- VSCodium does not use the Microsoft Marketplace because the Marketplace terms restrict use to Microsoft products; it uses open-vsx.org (search summary). — [VSCodium README](https://raw.githubusercontent.com/VSCodium/vscodium/master/README.md)
- Open VSX is a single point of dependency for forks: a past outage of about 24 hours affected them (search result title). — [LibHunt post on the Open VSX outage](https://www.libhunt.com/posts/1424956-openvsx-which-vscode-forks-rely-on-for-extensions-down-for-24-hours)
- Pylance is licensed for Microsoft products only; Cursor users report `ms-python.vscode-pylance` is unsupported there due to licensing, and Cursor ships its own `anysphere.cursorpyright`, which some users report is weaker than Pylance (search summary of forum posts, 2024-2025). — [Cursor forum: Pylance licensing](https://forum.cursor.com/t/pylance-in-cursor-special-license-or-intentional-inducement-of-copyright-infringement/27794); [Cursor forum: Pylance fails to initialize](https://forum.cursor.com/t/pylance-server-fails-to-initialize-due-to-licensing-restriction/48548)
- In April 2025 Microsoft's C/C++ extension stopped working in VS Code forks including Cursor and VSCodium, showing that forks can lose functionality through upstream decisions outside their control. — [The Register, 24 April 2025](https://www.theregister.com/2025/04/24/microsoft_vs_code_subtracts_cc_extension/)
- basedpyright is an open-source fork of Pyright, available on Open VSX, and described by fork users as the closest open replacement for Pylance (search summary). — [Cursor forum: Pylance licensing](https://forum.cursor.com/t/pylance-in-cursor-special-license-or-intentional-inducement-of-copyright-infringement/27794)
- Void (open-source AI fork of VS Code): the project's repo note says the team paused work "to explore a few novel coding ideas"; the editor keeps running but without maintenance "some existing features might stop working over time"; the team will not actively review issues or PRs. Secondary blogs date the pause to January 2026. The repo does not attribute the pause to fork-maintenance cost. — [Void repo mirror](https://github.com/Haxford/void); [cursor-alternatives.com status post](https://cursor-alternatives.com/blog/void-editor-development-status-2026/)

### Inferences
- The Positron lesson generalises: a fork is survivable only if almost everything lives in extensions or additive contributions and the patch set against upstream is tiny. If the patch set is tiny, most of the value could have been an extension, which weakens the case for forking in the first place.
- For this project the fork's unique benefit is removing UI (activity bar items, Copilot entry points, command palette clutter) and making tutor guardrails non-bypassable. The first is cosmetic and partly achievable with settings; the second is not a real need for a self-directed student.
- Losing Pylance is tolerable for Python/PyTorch coursework because open language servers exist (basedpyright confirmed above), but losing Microsoft's Remote-SSH would matter given the remote GPU box requirement. I did not verify the current state of open Remote-SSH implementations this session.
- Void's pause is a data point about small-team AI forks stalling, not proof that rebasing killed it.

### Gaps
- Concrete numbers: hours per upstream merge, build times, CI cost, Apple Developer Program and notarization steps, auto-update infrastructure. No source found. (Background knowledge: VS Code ships roughly monthly, and macOS distribution outside the App Store needs a paid Apple Developer ID and notarization; not verified this session.)
- Current text of the Visual Studio Marketplace Terms of Use and the Pylance, Remote-SSH, and C# Dev Kit licences was not read; the restriction is reported here via VSCodium's README and forum/news sources.
- Status of Pyrefly (Meta) and ty (Astral) as of late 2026, and their Open VSX availability: the search returned nothing.
- Lessons from Cursor, Windsurf, Kiro, and Eclipse Theia / Theia AI: no sources retrieved. Kiro in particular returned nothing.
- Open Remote-SSH alternatives usable in forks: not researched.

## 3. Zed

### Takeaway
Zed cannot host a custom tutor panel through extensions, but it offers the cleanest "no fork" tutor route of any editor: point a custom Agent Client Protocol (ACP) agent at it with a few lines of settings, and Zed supplies the chat thread UI while the builder's own process supplies the tutor behaviour. Its extension surface is narrower and also in flux (agent-server and MCP-server extensions are being moved to registries).

### Cited Findings
- Zed's extension developer docs index lists guides for languages, themes, icon themes, debuggers, snippets, and MCP servers; it does not list slash commands or agent servers. — [Zed extensions docs](https://zed.dev/docs/extensions)
- Zed's own FAQ says extensions currently cover language support, debuggers, MCP servers, themes, and icon themes, and that the company intends to widen the surface later towards UI customisation (search summary). — [Zed extensions page FAQ](https://zed.dev/extensions/wit)
- Extensions are Rust compiled to WebAssembly (Component Model, run in Wasmtime) and cannot modify the UI or perform arbitrary operations (search summary of a mirror of Zed's blog). — [Mirror of "Life of a Zed Extension"](https://www.plushcap.com/content/zed/blog/life-of-a-zed-extension-rust-wit-wasm)
- A developer who wanted a native Claude Code dock panel in Zed had to build it into a fork because the extension API could not provide that UI (search summary; single blog post). — [dev.to, "Zed is amazing, I hate it"](https://dev.to/tunadev0/zed-is-amazing-i-hate-it-5aob)
- Agent-server (ACP) extensions "have been deprecated in favor of the ACP Registry as of v1.5.0"; previously installed extension agents are migrated to registry equivalents (search summary). — [Zed agent-server extension docs](https://zed.dev/docs/extensions/agent-servers.md); [Zed external agents docs](https://zed.dev/docs/ai/external-agents.html)
- MCP server extensions are listed as planned for deprecation in favour of the official MCP registry (search summary). — [Zed docs index via search](https://docsearch.algolia.com/mcp/docs/repo/zed-industries/zed)
- External agents run as separate processes over ACP; Zed hosts the thread in the Agent Panel and Threads Sidebar while the agent "usually manages its own runtime, auth, model selection, tools, and native configuration". Zed does not charge for external agents. — [Zed external agents docs](https://zed.dev/docs/ai/external-agents)
- A custom ACP agent is added in settings without any extension or registry entry:
  `"agent_servers": { "my-agent": { "type": "custom", "command": "node", "args": ["~/projects/agent/index.js", "--acp"], "env": {} } }` — [Zed external agents docs](https://zed.dev/docs/ai/external-agents)
- For external agents: Zed Agent profiles do not apply unless the integration says so; Zed Skills do not apply; tool permissions depend on both Zed's ACP forwarding and the agent's native rules; Zed MCP servers may be forwarded over ACP; Zed's LLM provider settings and API keys do not configure external agents. — [Zed external agents docs](https://zed.dev/docs/ai/external-agents)
- Claude Agent is installable from the ACP Registry, "owns its own authentication and billing", is logged into via `/login` with an API key or Claude Code auth "where supported", and may read `CLAUDE.md` directly. — [Zed external agents docs](https://zed.dev/docs/ai/external-agents)
- `"disable_ai": true` turns off all AI features: Threads Sidebar, Agent Panel, Edit Prediction, and Inline Assistant. — [Zed AI quick start](https://zed.dev/docs/ai/quick-start)

### Inferences
- A tutor-in-Zed design: write a small ACP agent (for example on the Claude Agent SDK with read-only tools), register it as a custom `agent_servers` entry, turn off edit predictions, and use Zed's built-in thread UI. This gets chat, explain-error, and code review with zero UI code. It cannot get inline hint decorations, a learner-progress panel, or spaced-repetition UI, because there is no extension UI surface.
- `disable_ai: true` appears to disable the Agent Panel itself, which is where an ACP tutor would live. So the "tutor only" configuration is likely "AI on, edit predictions off, default agent replaced", not `disable_ai`. This needs testing.
- Alternatively, an MCP server exposing tutor tools can be attached to Zed's own agent, but then the tutor's behaviour depends on Zed's agent prompt and profiles rather than the builder's harness.
- Zed is a good fit for the student's own daily use on macOS and a weak fit as the long-term product form if the product needs any bespoke UI.

### Gaps
- Zed's licence and the implications of forking it: no source retrieved. (Background knowledge, unverified this session: the editor is GPL-3.0-or-later, server-side collaboration components AGPL, and the GPUI framework Apache-2.0; a fork distributed to others would have to be GPL-licensed.) The report writer should confirm against the Zed repository before relying on this.
- Whether slash-command extensions still exist in late 2026 (they are absent from the current docs index, which suggests removal or relocation, but I found no explicit statement).
- Zed custom agent profiles and rules files: not read this session.
- Which Zed version introduced the ACP Registry beyond the "v1.5.0" deprecation note, and Zed's Python tooling defaults and remote-development (SSH) support, were not checked.

## 4. Custom editor from components

### Takeaway
A custom Tauri or Electron app around CodeMirror 6 or Monaco gives total control over simplicity and tutor UX, but the editing surface is the small part: language intelligence, terminal, test running, debugging, notebooks, and remote execution are each a project. I found size and memory figures for the shells and editor components, but almost no primary sources this session on the integration effort, so effort estimates below are inference.

### Cited Findings
- Tauri vs Electron size: one July 2026 test reports a Tauri hello-world at 3.2 MB vs 85 MB for Electron 34.x; another measured Tauri at 57 MB, Electron at 323 MB for a comparable app. Typical claims are 3-10 MB for Tauri vs 80-200 MB for Electron. Sources disagree on magnitude and are mostly low-quality blogs (search summary). — [tech-insider.org](https://tech-insider.org/tauri-vs-electron-2026/); [Better Stack comparison](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/)
- Memory: idle claims range from roughly 30-50 MB for Tauri, with one figure of 42 MB vs 168 MB for Electron; a macOS hands-on comparison found Electron's Chromium renderers used about double the memory of Tauri's WKWebView for the same window (search summary). — [dev.to / gethopp comparison](https://dev.to/gethopp/tauri-vs-electron-performance-bundle-size-and-the-real-trade-offs-1el4); [tech-insider.org](https://tech-insider.org/tauri-vs-electron-2026/)
- Tauri uses the OS webview, so rendering differs across platforms; apps depending on Chromium-only APIs or pixel-exact rendering need real cross-platform testing (search summary). — [digitalapplied.com decision matrix, June 2026](https://www.digitalapplied.com/blog/desktop-apps-web-stack-tauri-electron-deno-wails-2026)
- Monaco vs CodeMirror 6 bundle size: figures vary widely. Replit reported monaco-editor and related libraries at 51.17 MB in its bundle (5.01 MB parsed and gzipped); a 2026 guide estimates Monaco at about 5 MB gzipped vs 50-200 kB for CodeMirror 6 depending on features (search summary). — [Replit, "Betting on CodeMirror"](https://replit.com/blog/codemirror); [pkgpulse 2026 guide](https://www.pkgpulse.com/guides/monaco-editor-vs-codemirror-6-vs-sandpack-in-browser-2026)
- Monaco ships built-in language services for TypeScript/JavaScript/JSON/CSS/HTML (not Python); CodeMirror 6 is modular and suited to custom editors where modularity matters more than pre-built IDE features (search summary). — [techinterview.org comparison](https://www.techinterview.org/post/3233475355/build-code-editor-codemirror-monaco-tradeoffs/)
- Both Sourcegraph and Replit migrated from Monaco to CodeMirror 6 and wrote it up; Replit noted at the time that the CodeMirror 6 community was young and "we have to write many things ourselves" (search summary; that remark is several years old). — [Sourcegraph migration post](https://sourcegraph.com/blog/migrating-monaco-codemirror); [Replit, "Betting on CodeMirror"](https://replit.com/blog/codemirror)
- Thonny, the best-known beginner Python IDE, is written in Python on Tkinter, has a plugin architecture, and a debugger designed specifically for learning (search summary). — [Wikipedia: Thonny](https://en.wikipedia.org/wiki/Thonny); [Podcast.__init__ episode 153](https://dev.to/podcast__init__/thonny-the-ide-for-beginning-programmers-with-aivar-annamaa--episode-153)

### Inferences
- On macOS only, Tauri's main weakness (webview inconsistency across OSes) mostly disappears, since there is one webview (WKWebView). Its remaining costs for this project are a Rust backend the builder must write in, and running Node- or Python-based helpers (language servers, a Claude Agent SDK process) as sidecar processes. Electron gives Node in-process, which makes node-pty, LSP clients, and the TypeScript Agent SDK straightforward, at the cost of a roughly 100 MB larger download. For a solo builder whose time is the binding constraint, Electron is the lower-risk shell; Tauri is the nicer artefact.
- For a deliberately minimal single-language editor, CodeMirror 6 is the better surface: small, composable, and easy to strip down. Monaco's advantage (VS Code-like behaviour out of the box) matters less when Python intelligence must come from an external language server either way.
- Rough effort for a usable MVP (my estimate, no source): file tree + CodeMirror editor + tutor chat panel + "run file" in an embedded terminal is on the order of weeks part-time. Adding LSP diagnostics/hover/completion via basedpyright and ruff, pytest result parsing, and persistent sessions pushes it to a few months. Debugging (DAP with debugpy), Jupyter kernels, and remote SSH execution are each comparable to the whole first MVP, and are where solo editor projects typically stall.
- Commonly underestimated items (background knowledge, not sourced this session): Python environment discovery (venv/conda/uv) and interpreter selection; LSP lifecycle and document-sync edge cases; terminal quirks (resizing, shell integration, colour, signals); file watching and external-change reconciliation; undo history across AI interactions; find/replace and multi-file search; keybinding expectations; macOS signing, notarization, and auto-update; and remote execution (port forwarding, file sync, kernel lifetime).
- The remote GPU box is the single requirement most likely to push this approach back towards VS Code or Zed, both of which already have remote development; rebuilding that alone is disproportionate. A pragmatic custom-editor stance would be "edit locally, run remotely over plain SSH in the terminal pane" and nothing more.

### Gaps
- No sources retrieved this session on: codemirror LSP client packages and their maturity; Tauri 2 sidecar (`externalBin`) and PTY plugins (for example portable-pty-based ones); xterm.js + node-pty; pytest result parsing (JUnit XML or `pytest-json-report`); Debug Adapter Protocol and debugpy; Jupyter kernel protocol (ZeroMQ messaging, `jupyter_client`); remote/SSH execution patterns.
- Effort signals from Lapce, Pulsar, marimo's editor, and Theia (commit history, contributor counts, years to usable): the search returned nothing. This sub-question is unanswered.
- Current Electron and Tauri versions and release cadence: sources conflicted (one cites Electron 44.0.0 on 25 August 2026, others benchmark 33-34), so I am not reporting a version.
- All size and memory figures above are from secondary blogs with differing methodologies; treat as order-of-magnitude only.

## 5. Lighter-weight alternatives that avoid building an editor

### Takeaway
The lowest-effort credible tutor is configuration, not software: Claude Code already ships a built-in "Learning" output style that makes the student write parts of the code, and styles, hooks, and permission rules can be packaged as a plugin. An MCP server or ACP agent carrying the tutor tools is the most portable artefact, since it works across Claude Code, VS Code, Zed, and marimo; what none of these can do is add bespoke editor UI or stop the student from opening a different, unrestricted assistant.

### Cited Findings
- Claude Code has built-in output styles including Explanatory and Learning; in Learning style Claude adds "Insight" blocks and "also has you write some of the code", leaving `TODO(human)` markers for the student to implement (search summary; the `TODO(human)` detail comes from localised versions of the docs). — [Claude Code output styles docs](https://code.claude.com/docs/en/output-styles)
- Output styles work by changing the system prompt Claude Code gives the model; they are selectable via `/config`, the VS Code extension's `/` menu, or an `"outputStyle"` setting, and take effect at session start (search summary). — [Claude Code output styles docs](https://code.claude.com/docs/en/output-styles)
- Plugins can ship custom output styles in an `output-styles/` directory and a plugin can set a style to apply automatically (search summary). — [Claude Code output styles docs](https://code.claude.com/docs/en/output-styles)
- Explanatory and Learning styles produce longer responses by design and so use more output tokens (search summary). — [Claude Code output styles docs](https://code.claude.com/docs/en/output-styles)
- Claude Code / Agent SDK permission evaluation order is: hooks, then deny rules, then ask rules, then permission mode, then allow rules, then the `canUseTool` callback. Deny rules apply even in `bypassPermissions` mode and even when a hook returned allow. — [Agent SDK permissions docs](https://code.claude.com/docs/en/agent-sdk/permissions)
- Allow/deny/ask rules can be declared in a project's `.claude/settings.json`, so a course repo can carry its own restrictions. — [Agent SDK permissions docs](https://code.claude.com/docs/en/agent-sdk/permissions)
- Plugins package skills, agents, hooks, and MCP servers. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- marimo's built-in AI: custom rules can be added in settings to steer the assistant; a notebook access selector limits the assistant from read-only up to full access (which can run cells); `[ai] enabled = false` hides in-editor AI; completion is separate from chat; an experimental Agents panel connects ACP-compatible agents; "marimo pair" lets external agent CLIs such as Claude Code work on a live notebook session (search summary). — [marimo AI completion docs](https://docs.marimo.io/guides/editor_features/ai_completion/); [marimo agents docs](https://docs.marimo.io/guides/editor_features/agents/); [marimo: using Claude Code](https://docs.marimo.io/guides/generate_with_ai/using_claude_code/)
- In VS Code, MCP tools run outside the editor and cannot access VS Code extension APIs; an agent plugin can bundle an MCP server with skills and a custom agent. — [VS Code AI extensibility overview](https://code.visualstudio.com/api/extension-guides/ai/ai-extensibility-overview)
- In Zed, a custom ACP agent is a settings entry; Zed MCP servers may be forwarded to external agents over ACP. — [Zed external agents docs](https://zed.dev/docs/ai/external-agents)

### Inferences
- What each option can enforce:
  - Claude Code plugin (output style + deny rules for `Edit`/`Write`/`NotebookEdit` + hooks): can make file writes impossible at the harness level (deny rules hold in every mode) and steer behaviour via the system prompt. It cannot stop the model pasting a full solution into chat as text (that needs a Stop/response-side hook or a second-pass check), cannot add UI, and the student can disable the plugin. Note the built-in Learning style still has Claude write most of the code and leave gaps, which is looser than "does not write the code for them"; a custom style is needed.
  - MCP server exposing tutor tools (get_hint with escalation levels, explain_error, review_diff, record_attempt, quiz_due_items): portable to any MCP client and a natural home for the learner model in SQLite. It enforces nothing on its own: the host agent decides whether to call it and can still write code with its own tools.
  - ACP agent: the builder owns the whole harness, so guardrails are as strong as in a custom app, and Zed and marimo (experimental) supply the UI. No bespoke UI.
  - Terminal companion watching the repo and test runs: fully editor-agnostic, can react to failing pytest runs and git diffs, and has no write access by construction. Interaction is confined to the terminal; no inline anchoring to code.
  - JupyterLab or marimo extension: best fit if coursework is notebook-first. marimo's read-only access level plus custom rules approximates a tutor today with no code. Not a fit for multi-file PyTorch projects or remote training runs.
  - Neovim plugin: full control of UI within Neovim's limits, but only sensible if the student already lives in Neovim.
- The cheapest experiment with the highest information value is: custom Claude Code output style + deny rules on write tools + a small MCP server for hints and the learner model, used inside whatever editor the student already has. It can be built in days and tests whether tutor-mode behaviour is actually what the student wants before any editor work.

## 6. LLM integration: Claude API, Agent SDK, cost, keys, local models, guardrails

### Takeaway
Token cost is not the constraint: with prompt caching, one heavy student user on Claude Sonnet 5.5 comes to roughly $25-40 a month by my estimate, and a few dollars on Haiku 5.5. The real design decisions are (1) bring-your-own API key is effectively mandatory for anything distributed, because Anthropic does not let third-party products offer claude.ai login, and (2) guardrails should be layered: remove write tools at the harness (strong), instruct via system prompt (moderate), and add a cheap second-pass check on outgoing text (moderate), since no prompt-only approach reliably stops full solutions appearing in chat.

### Cited Findings

Claude Agent SDK as a constrained tutor harness:
- The Agent SDK is Claude Code as a Python/TypeScript library: built-in tools (read, write, edit files, run commands, web search), hooks, subagents, MCP, permissions, sessions, skills/commands/memory loaded from `.claude/`, and plugins. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Authentication: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods described in the Quickstart instead." — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Use of the Agent SDK is governed by Anthropic's Commercial Terms of Service; products must keep their own branding and may not present as "Claude Code". — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- The documented locked-down pattern is `allowedTools: ["Read", "Glob", "Grep"]` with `permissionMode: "dontAsk"`: listed tools are approved and every other call that would prompt is denied. — [Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- Caveat on that pattern: calls that need no approval in default mode still run whether or not listed, including read-only Bash commands, file reads in the working directory, and the `Agent` (subagent) tool. To hide a built-in tool entirely, add its bare name to `disallowedTools`; `disallowed_tools=["Bash"]` removes the Bash tool definition from the request. — [Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- Deny rules are enforced in every permission mode including `bypassPermissions`, and a hook deny also applies in `bypassPermissions`. `Edit(path)` rules govern all built-in file-writing tools (Write, NotebookEdit). A script the agent runs via Bash can still write files unless Bash is removed or sandboxed. — [Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- Permission modes available: `default`, `dontAsk`, `acceptEdits`, `bypassPermissions`, `plan`, `auto`. With Claude Code v2.1.302 or later an SDK app starts in `default`, where calls needing approval are denied unless approved by a rule, hook, or callback. — [Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- In Zed, the registry "Claude Agent" owns its own authentication and billing and is logged in with an API key "or with Claude Code where supported". — [Zed external agents docs](https://zed.dev/docs/ai/external-agents)

### Inferences
- Monthly cost estimate for one heavy student user (my arithmetic from the prices above; assumptions: 60 tutor requests per working day, 22 days, about 1,300 requests per month; each request carries a 30,000-token cached prefix of course material and repo context, 3,000 fresh input tokens, and 1,000-1,500 output tokens including thinking; about 100 cache writes per month of the 30,000-token prefix at the 5-minute rate):
  - Sonnet 5.5: per request about $0.003 (cache read) + $0.006 (fresh input) + $0.010-0.015 (output) = about $0.02-0.025; about $25-32 per month, plus about $7.50 in cache writes; roughly $30-40 per month.
  - Opus 5.5: per request about $0.006 + $0.012 + $0.020-0.030 = about $0.04-0.05; about $50-62 per month plus about $15 in cache writes; roughly $65-80 per month.
  - Haiku 5.5: per request about $0.001; under $3 per month including writes.
  - Same Sonnet 5.5 workload without caching: about 33,000 input tokens at $2/M = $0.066 plus output, about $0.08 per request, roughly $100 per month. Caching cuts the bill by about two thirds.
  - These token counts are guesses; the tokenizer note (about 30% more tokens on current models) and long review sessions could move them by a factor of two either way.
- Model choice for tutoring: Sonnet 5.5 as the default tutor, with Haiku 5.5 for the cheap second-pass "is this a full solution?" check and for spaced-repetition item generation, looks like the sensible split. Opus 5.5 is affordable for a single user if deeper explanations of research papers are wanted.
- Feature fit (from Anthropic's bundled API reference loaded in this session, cached 2026-11-03, not a public URL): PDF input is supported as base64 or via the Files API (limits 32 MB per request and 600 pages); citations are enabled per document block and return page locations for PDFs, which suits "show me where the handout says this", but citations are incompatible with structured outputs in the same request; structured outputs use `output_config.format`; adaptive thinking with an `effort` setting replaces fixed thinking budgets on current models; the Files API is out of beta. The report writer should link the public docs for these before quoting them.
- Key handling: for a personal tool the student simply uses their own API key (stored in macOS Keychain, not a dotfile). If the tool is ever distributed, bring-your-own-key is the only route consistent with the Agent SDK note above unless Anthropic approves otherwise. The student's existing Claude subscription can be used legitimately through Anthropic's own surfaces (Claude Code itself, or Claude Agent inside Zed), which is an argument for the plugin/ACP route in the early phase: no per-token bill at all.
- Local models: usable as an offline or privacy fallback for simple explain-error on a 32 GB Mac, but I found no evidence on tutoring quality specifically, and the pedagogically hard part (withholding the answer while diagnosing a misconception accurately in PyTorch code) is where weaker models tend to fail. Given cloud cost of a few tens of dollars a month, local-first is not justified on cost grounds; it is justified only by privacy or offline needs.
- Guardrail reliability, strongest to weakest (my assessment):
  1. Tool restriction at the harness (no Write/Edit/NotebookEdit, no Bash or sandboxed read-only Bash): deterministic. The tutor cannot change files. Does not stop solution text in chat.
  2. UI affordances: no "apply" or "insert" button on code blocks, code blocks limited in length or rendered as non-copyable hints. Deterministic but trivially bypassed by retyping; still useful friction.
  3. System prompt / output style defining tutor behaviour with a hint ladder (question, concept pointer, pseudocode, minimal snippet): effective most of the time with current models, degrades under persistent user pressure ("just give me the code"). Probabilistic.
  4. Second-pass classifier (cheap model or heuristic: runnable code block longer than N lines that would complete the student's TODO or make the failing test pass) that blocks or rewrites the response: catches a good share of slips at small cost and added latency; has false positives on legitimate worked examples. Probabilistic.
  5. Structured hint tools (the model must call `give_hint(level, text)` and the app renders only that): narrows the output channel and makes policy checkable in code.
  For a self-directed student the realistic goal is "the default path never hands over a solution, and getting one requires a deliberate, logged override", not adversarial robustness.

## 7. Local data needs: learner model, hint history, retrieval, privacy

### Takeaway
Nothing here needs infrastructure beyond a single local SQLite file, and at one student's scale the course corpus may not need a retrieval index at all, since current Claude models take 1M tokens of context at standard pricing with cheap cache reads. I did not find or search for dedicated sources on this question, so this section is mostly inference.

### Cited Findings
- Claude 4.6 and later models (except Haiku 5.5) include a 1M-token context window at standard per-token pricing, and caching discounts apply across the full window. — [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- A 500 kB research-paper PDF is about 125,000 tokens when fetched as content. — [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Cache reads cost $0.10 per million tokens on Sonnet 5.5 and $0.20 on Opus 5.5; a 1-hour cache write costs 2x base input. — [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Claude Fable 5.2 requires 30-day data retention and is not available under zero data retention unless authorised (from Anthropic's bundled API reference, cached 2026-11-03; no public URL fetched). — [Claude pricing page for the model's existence and price](https://platform.claude.com/docs/en/about-claude/pricing)

### Inferences
- Storage: one SQLite database (with FTS5 for keyword search) covers the learner model (concept, mastery estimate, last-seen, evidence), hint history (prompt, hint level, whether the student then solved it), spaced-repetition items (card, due date, interval, ease), and session logs. No server, trivially backed up, and inspectable by the student. This is the same whether the front end is an MCP server, a VS Code extension, or a custom app, which is a reason to put the data layer in the MCP server or a small local service from day one so it survives any change of front end.
- Retrieval: for a single course, "load the relevant week's handout and transcript into a cached prefix" is simpler and more accurate than a vector index. A 100,000-token cached prefix on Sonnet 5.5 costs about $0.01 per request to read and about $0.40 per 1-hour cache write (my arithmetic from the prices above). A whole-term corpus of slides, papers, and transcripts will exceed what is sensible to send every time, so a lightweight index (SQLite FTS5 keyword search first; embeddings via a local model or the sqlite-vec extension only if keyword search proves inadequate) is the next step, with the tutor fetching sections through a `search_course_material` tool. Citations with page locations make the retrieved text verifiable.
- Privacy: the sensitive items are the student's own code and mistakes (the learner model), course materials that may be copyrighted or under instructor distribution rules, and any graded assignment text. Keeping the database local and sending only the needed context to the API is the natural default. If the tool is only ever for the builder, institutional rules (FERPA-type obligations) do not arise; they would if other students' data were collected. Academic-integrity policy for each course is a separate, non-technical constraint the tool should make easy to respect (for example, a per-repo setting that restricts the tutor to concept-level hints on graded work).
- The API key should live in the macOS Keychain.

### Gaps
- No sources were retrieved on SQLite vector extensions, embedding options (Anthropic does not, to my knowledge, offer a first-party embeddings model; unverified), PDF and transcript chunking practice, or spaced-repetition algorithms (SM-2, FSRS).
- Anthropic's API data-retention and training-use policy for standard API traffic was not fetched; the report writer should cite the current commercial terms or privacy documentation rather than this note.

## 8. Overall comparison: most sensible starting point and long-term form

### Takeaway
Start with configuration and a portable tutor core (Claude Code custom output style and deny rules, plus an MCP server or ACP agent holding the hint tools and the SQLite learner model) used inside an existing editor; grow into a VS Code extension with its own webview panel calling the Claude API directly once bespoke UI is needed. A fork is not justified for a solo part-time builder, and a custom editor is a reasonable long-term form only if the scope is held to "editor + terminal + tutor" and remote/debug/notebook features are consciously given up.

### Cited Findings
- VS Code's chat participant route is deprecated with its harness due for removal in February 2027; agent plugins (skills + MCP server + optional custom agent) are the recommended replacement. — [VS Code AI extensibility overview](https://code.visualstudio.com/api/extension-guides/ai/ai-extensibility-overview); [Chat Participant API guide](https://code.visualstudio.com/api/extension-guides/ai/chat)
- Zed accepts a custom ACP agent via a settings entry and supplies the thread UI; its extensions cannot add UI. — [Zed external agents docs](https://zed.dev/docs/ai/external-agents); [Zed extensions FAQ](https://zed.dev/extensions/wit)
- Claude Code supports plugin-shipped output styles and harness-level deny rules that hold in every permission mode. — [Claude Code output styles](https://code.claude.com/docs/en/output-styles); [Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- Forks lose Microsoft's proprietary extensions and carry a continuing merge burden; Void, a small open-source AI fork, paused development. — [VSCodium README](https://raw.githubusercontent.com/VSCodium/vscodium/master/README.md); [EclipseSource on forking](https://eclipsesource.com/blogs/2024/12/17/is-it-a-good-idea-to-fork-vs-code/); [Void repo mirror](https://github.com/Haxford/void)
- Third-party products built on the Agent SDK must use API-key authentication, not claude.ai login. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

### Inferences
Comparison (all effort figures are my estimates for one part-time student; none are sourced):

| Approach | Effort to first useful version | Capability ceiling | Maintenance burden | Licensing constraints | Running cost |
|---|---|---|---|---|---|
| Claude Code plugin (output style, deny rules, hooks) + MCP tutor server | Days | Chat, hints, explain-error, review; no custom UI; guardrails strong on writes, soft on chat text | Low; follows Claude Code releases | Anthropic terms; own subscription usable | Subscription already held, or API at roughly $30-40/month on Sonnet 5.5 |
| ACP tutor agent in Zed (or marimo) | About 1-2 weeks | Same as above with builder-owned harness; Zed supplies thread UI; no custom panels | Low to moderate; ACP and Zed's agent surface are still moving (registry migration at v1.5.0) | API key required for own agent | API, as above |
| VS Code extension with own webview + direct Claude API | About 3-8 weeks for chat, explain-error on diagnostics, review, CodeLens hints | High: inline decorations, panels, test and terminal hooks, notebooks, Remote-SSH and Pylance come free in Microsoft's build | Moderate; stable APIs, but AI-specific APIs are churning (avoid chat participants) | Fine as an extension; publish to both Marketplace and Open VSX for forks | API, as above |
| VS Code agent plugin inside Copilot chat | About 1-2 weeks | Limited to what Copilot's harness allows; tutor shares a surface with a code-writing agent | Moderate; newest and least settled surface | Likely needs Copilot (unverified) | Copilot plan plus any API use |
| Custom app (Electron or Tauri + CodeMirror 6 + LSP + terminal) | About 2-4 months for an MVP; much longer with debugging, notebooks, remote | Unlimited in principle; in practice bounded by what one person can build and keep working | High and permanent; builder owns everything including signing and updates | Free choice; open components | API, as above, plus an Apple Developer account if distributed |
| VS Code fork | Months before parity plus tutor features | Full workbench control | Very high; monthly upstream merges, build and release infrastructure | No Microsoft Marketplace, Pylance, or Microsoft Remote-SSH | API plus build infrastructure |
| Zed fork | Months; Rust and GPUI expertise needed | Full control, native performance | Very high | Copyleft (unverified this session) | API |

- Most sensible starting point: the Claude Code plugin plus MCP tutor server. It is the only option measured in days, it uses a subscription the student likely already has, its write-blocking is deterministic, and its two durable assets (the tutor prompt/hint policy and the SQLite learner model behind MCP tools) carry forward unchanged into every other option.
- Most sensible long-term form: a VS Code extension with its own webview tutor panel that calls the Claude API (or embeds the Agent SDK) directly, sets `chat.disableAIFeatures` and a pared-down profile, and reuses the same MCP/SQLite core. It gets Python tooling, debugging, notebooks, and the remote GPU box for free, works in forks via Open VSX if it avoids Copilot-specific APIs, and is insulated from the chat-participant deprecation.
- When the custom editor becomes the better long-term form: if "deliberately minimal" is the product itself (the student finds VS Code's surface area is the problem even after a stripped profile), and remote work can be reduced to an SSH terminal pane. In that case Electron + CodeMirror 6 + basedpyright + xterm.js with the same tutor core is the pragmatic stack on macOS, and the extension phase will already have settled what the tutor UX should be.
- A fork of either editor is hard to justify at this scale: its unique benefit (removing UI, non-bypassable guardrails) is not needed by a self-directed user, and its costs fall entirely on one part-time person.

### Gaps

- Whether a VS Code agent plugin requires a Copilot subscription, and how well a custom agent there can be confined to tutor behaviour, was not established.
- No user-research or pedagogy sources were consulted (out of scope for this note); whether the hint-ladder tutor design actually improves learning is assumed, not shown.
