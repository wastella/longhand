# CS336 and from-scratch ML-systems coursework: student workflow, AI policy, pain points and tooling needs (as of 26 Nov 2026)

Method note: primary sources (course site HTML, assignment handout PDFs, repo files, the course's AI-policy Google Doc, GitHub issues) were downloaded and read directly on 26 Nov 2026; policy quotes below are verbatim from those files. "2026" means the Spring 2026 offering (current site at cs336.stanford.edu, handout versions 26.x); "2025" means the archived Spring 2025 site. Where a claim comes from a blog, a forum mirror, or a tool-generated summary rather than a primary file, that is stated.

## 1. CS336 structure: assignments, what is provided vs. implemented, repo layout, deliverables, compute

### Takeaway
CS336 is five implementation-heavy assignments (Basics, Systems, Scaling, Data, Alignment/Reasoning RL) in which the student starts from an essentially empty Python package and wires their own code to provided pytest suites through a glue file `tests/adapters.py`; deliverables are a typeset `writeup.pdf`, a `code.zip`, and optional GitHub-PR leaderboards. The 2026 handouts budget compute in "B200 hours" (about 17 for A1, about 26 for A5, an 8-GPU run for A4), with explicit "Low-Resource Tips" for CPU/Apple Silicon in A1 only.

**Assignment 1 (Basics), handout v26.0.3, 47 pages**

The training loop, with support for serializing and loading model and optimizer state." What they run: BPE training on TinyStories, dataset encoding, LM training on TinyStories, sampling and perplexity evaluation, then OpenWebText training with a leaderboard submission. — [A1 handout PDF](https://github.com/stanford-cs336/assignment1-basics/blob/main/cs336_assignment1_basics.pdf)

### Inferences
- A student's day is a loop of: read a handout section (prose + math + a "Problem (name)" box with a Deliverable line), write a module in an empty package, add a one-line adapter, run a single pytest (`uv run pytest -k test_name`), then, later, run long experiments, log curves, and write typeset answers. An editor for this course needs first-class objects for "handout problem", "adapter", "test", "experiment run" and "writeup answer", not just files.
- Because the package starts empty, students make all structural decisions (file layout, class design, config handling, training script CLI). That design freedom is part of the pedagogy and is exactly what generative AI would erase.
- Roughly a third of A1's problems and much of A2/A3/A5 are written answers, derivations, plots, and resource accounting. Support for the writeup (collecting plots, run metadata, short typeset answers keyed to problem names) is as much a need as code support.
- Summing the handout's own labels gives about 17 B200-hours for A1 experiments (10 of them the optional-in-spirit leaderboard) and about 26 for A5; A4's reference run is about 16 B200-hours (8 GPUs for 2 hours). These sums are mine, computed from the per-problem labels cited above.

## 2. CS336's official AI policy and honor-code language, its evolution, and comparable courses

### Takeaway
CS336's wording tightened each year: 2024 allowed LLMs for "low-level programming questions or high-level conceptual questions" but not solving the problem; 2025 added a strong recommendation to disable AI autocomplete; 2026 made it a rule ("All your code should be handcrafted by you directly"; no agents, no AI autocomplete) and shipped an `AGENTS.md`/`CLAUDE.md` in every assignment repo instructing any AI agent to behave as a Socratic TA that writes no code or pseudocode. Comparable courses are noticeably more permissive (CS224N and CMU Deep Learning Systems explicitly allow Copilot/ChatGPT as collaborators or assistants), which makes CS336's 2026 policy the strictest, and the most operationally specific, of the set.

**The repo's AGENTS.md / CLAUDE.md (identical files; added to A1 on 6 Apr 2026, later copied to A2, A3, A5)**
- Title and role: "AI Agent Guidelines for CS336 at Stanford... Primary Role: Teaching Assistant, Not Solution Generator. AI agents should function as teaching aids that help students learn through explanation, guidance, and feedback—not by completing assignments for them." — [assignment1-basics/CLAUDE.md](https://github.com/stanford-cs336/assignment1-basics/blob/main/CLAUDE.md)
- "What AI Agents SHOULD Do" (verbatim list): "Explain concepts when students are confused by guiding them in the right direction and making sure they build the understanding themselves"; "Point students to relevant lecture materials (cs336.stanford.edu), handouts, official documentation, and profiling/debugging tools."; "Review code that students have written and suggest improvements, edge cases, invariants, or debugging checks. Feedback should be general and point the students to areas of improvements rather than directly giving them solutions."; "Help debug by asking guiding questions rather than providing fixes."; "Explain error messages from Python, PyTorch, CUDA, Triton, and distributed training tools."; "Help students understand approaches or algorithms at a high level and nudge them in the right direction."; "Suggest sanity checks, toy examples, assertions, and profiler-based investigations through active dialog with the student." — [assignment1-basics/CLAUDE.md](https://github.com/stanford-cs336/assignment1-basics/blob/main/CLAUDE.md)
- "What AI Agents SHOULD NOT Do" (verbatim list): "Write any python or pseudocode"; "Give solutions to any problems."; "Complete TODO sections in assignment code."; "Edit code in the student repo"; "Run bash commands"; "Refactor large portions of student code into a finished solution."; "Convert assignment requirements directly into working code."; "Implement core assignment components for students, such as tokenizers, transformer blocks, optimizers, training loops, Triton kernels, distributed training logic, scaling-law pipelines, data filtering/deduplication pipelines, or alignment/RL methods."; "Point students to third-party implementations. The course materials are intended to be self-contained."; "Give the student the solution or idea for how to solve a problem". — [assignment1-basics/CLAUDE.md](https://github.com/stanford-cs336/assignment1-basics/blob/main/CLAUDE.md)
- "Teaching Approach" includes "Ask clarifying questions about what they tried, what they expected, and what happened", "Reference concepts from lecture, handouts, or documentation rather than giving direct answers", "Suggest next steps instead of implementing them", and "Prefer tests and invariants over fixes. For example, suggest shape assertions, tiny toy inputs, profiler checks, or ablations." — [assignment1-basics/CLAUDE.md](https://github.com/stanford-cs336/assignment1-basics/blob/main/CLAUDE.md)
- Its model "Good" exchange: the agent first replies "My role is to help guide you to understanding, not to give you the answers directly. What have you tried so far?" and then offers three things to check about a causal mask plus "A good sanity test is a toy sequence of length 3 where you print the attention scores before and after masking." The "Bad" exchange is "Fix my tokenizer and make it faster." answered with "Here's the full python code: ...". — [assignment1-basics/CLAUDE.md](https://github.com/stanford-cs336/assignment1-basics/blob/main/CLAUDE.md)
- Closing rule: "AI tools may be used for low-level programming help and high-level conceptual questions, but not for directly solving assignment problems. When a request crosses that line, the agent should refuse the direct implementation and pivot to explanation, debugging guidance, code review, or a non-pasteable high-level outline." — [assignment1-basics/CLAUDE.md](https://github.com/stanford-cs336/assignment1-basics/blob/main/CLAUDE.md)
- The gist that inspired it is looser: it allows small illustrative code examples "(2-5 lines)" and ends "When in doubt, explain more and code less." (as summarized by a fetch of the gist). — [1cg gist](https://gist.github.com/1cg/a6c6f2276a1fe5ee172282580a44a7ac)
- Enforcement, per a course TA (marcelroed) in a Hacker News thread (read via a mirror): honor-code violations are caught through autograding, manual code audits and Modal submission logs, and large code deltas in short periods are reviewed, with "300 lines in 5 minutes" given as an example. — [HN thread 48357075 (mirror)](https://hn.nuxt.dev/item/48357075)
- Secondary coverage (dev.to, logicity, aitoolly, lavx) claims students must log or submit their AI interaction history. I found no such requirement in the policy doc, handout statement, or AGENTS.md; treat it as unverified. — [dev.to summary](https://dev.to/onsen/ai-agent-guidelines-for-cs336-at-stanford-jbi); contradicted by absence in [CS336 AI Policy doc](https://docs.google.com/document/d/1SZAlExB1qAc9izHt54gwunNpjKE6wXb8Y7yA_e-baK8/edit?tab=t.0)

### Inferences
- The trajectory is from "be reasonable" (2024) to "please turn off autocomplete" (2025) to "no AI-written code at all, and here is the system prompt your agent must run under" (2026). The 2026 design delegates policy enforcement to the tool via a repo file. A student editor that reads and honors `AGENTS.md` natively (and cannot be trivially overridden) is directly aligned with how the course now expects AI to be configured.
- The AGENTS.md is stricter than what a human TA does in places ("Write any python or pseudocode", "Run bash commands", "Edit code in the student repo" are all prohibited). An editor built for this must separate student-initiated execution (running tests, profilers) from agent-initiated action, and should not let the assistant edit or run anything.
- There is an internal tension worth designing around: the SHOULD list asks for code review and "likely bugs", while the SHOULD NOT list forbids giving "the solution or idea". The policy resolves it with "through dialog rather than directly giving them the bugs" and "non-pasteable high-level outline". "Non-pasteable" is a useful design criterion.
- The "would a CA comply with this in office hours?" test is the cleanest single rubric for classifying requests.
- Other courses mostly treat AI as a collaborator with a "don't let it substantially complete the work" clause; none of those found provide a machine-readable policy. An editor that supports per-course policy profiles would need CS336's as the strict end and CMU's as the permissive end.
- For an auditor there is no enforcement, so the policy functions as a self-imposed commitment device; at least two self-studiers adopted it voluntarily (see section 7).

## 3. Pain points reported by students and self-studiers

### Takeaway
The recurring difficulties are (a) BPE training speed and memory, (b) silent or environment-dependent correctness problems (tests that pass on a wrong implementation, snapshot mismatches across platforms and library versions, dtype overflow that float32 tests never exercise), (c) environment and platform friction outside the Stanford setup (Windows, macOS memory lock-ups, CUDA/Triton/vLLM being Linux+NVIDIA only), and (d) materials an auditor simply cannot access (the A3 API, cluster-hosted data). A1 and A2 are consistently described as the hardest and slowest.

### Cited Findings

**BPE tokenizer performance and memory**
- The handout itself frames this as a known cliff: "≤ 30 minutes (no GPUs), ≤ 30 GB RAM" for TinyStories with the hint of under 2 minutes using multiprocessing; "≤ 12 hours (no GPUs), ≤ 100 GB RAM" for OpenWebText; it tells students to "use profiling tools like cProfile or py-spy" and to build a small "debug dataset" (the TinyStories validation set, "22K documents instead of 2.12M"). — [A1 handout](https://github.com/stanford-cs336/assignment1-basics/blob/main/cs336_assignment1_basics.pdf)
- One self-studier profiled with Scalene and found "a majority portion of my merge logic was slow because I was checking for merges in all of the original pre-tokens"; after optimization TinyStories took under 1.5 minutes but OpenWebText still took about 4.5 hours. — [dotvignesh Substack](https://dotvignesh.substack.com/p/building-a-byte-pair-encoding-tokenizer)
- A three-part optimization series reports OpenWebText BPE training going from over 10 hours to under 10 minutes through algorithmic changes, data structures, parallelism, Cython and C++ (figure from the Chinese version's summary, via search-result excerpt). — [fancyerii series, part 1](https://fancyerii.github.io/2025/09/07/bpe-trainer-1_en)
- Another write-up: "Tokenizer training is the hidden bottleneck" and "Pair frequency tables can grow to tens of GB." — [li-xiang blog, Feb 2026](https://blog.li-xiang.xyz/2026/02/09/CS336/CS336-Assignment-1-Building-a-Transformer-Language-Model-from-Scratch)
- A student reported `train_bpe` tests that "sometimes passed but sometimes failed on the same code" (nondeterminism in their implementation or tie-breaking). The 2024 changelog had to "clarify example of preferring lexicographically greater merges to specify that we want tuple comparison." — [issue #70](https://github.com/stanford-cs336/assignment1-basics/issues/70); [A1 CHANGELOG](https://github.com/stanford-cs336/assignment1-basics/blob/main/CHANGELOG.md)
- Open tokenizer-spec questions in 2026 issues: "Clarification on individual-token decoding in BPE tests" (#96), "Could you clarify the expected serialization format for Tokenizer.from_files?" (#94), "train bpe vocab definition" (#63). — [assignment1-basics issues](https://github.com/stanford-cs336/assignment1-basics/issues)

**Silent bugs and tests that do not catch them**
- "All tests in `test_tokenizer.py` pass despite faulty tokenizer": a naive `encode_iterable` that encodes each string independently splits pretokens across chunk boundaries, and the provided tests do not cover it. — [issue #88](https://github.com/stanford-cs336/assignment1-basics/issues/88)
- "Without casting to float32, the mean-of-squares computation can overflow in float16/bfloat16, leading to NaN losses... This is a subtle bug that wouldn't be caught by unit tests in float32." — [li-xiang blog](https://blog.li-xiang.xyz/2026/02/09/CS336/CS336-Assignment-1-Building-a-Transformer-Language-Model-from-Scratch)
- The leaderboard README warns "it's easy to measure your metrics wrong in a way that will place you higher on the leaderboard than you should be" and tells students to validate datasets "by checking decoded samples, and making sure your vocab is correct with 32k tokens." — [assignment1-basics-leaderboard README](https://github.com/stanford-cs336/assignment1-basics-leaderboard)
- The handout's own debugging advice targets this class of bug: "overfit to a single minibatch", "Set debug breakpoints in various model components, and inspect the shapes of intermediate tensors", "Monitor the norms of activations, model weights, and gradients". It also asks students to "explicitly verify that the memory-mapped data looks correct". — [A1 handout](https://github.com/stanford-cs336/assignment1-basics/blob/main/cs336_assignment1_basics.pdf)
- The handout warns of a silent backend failure: on MPS "do not use TF32 kernels... We tried enabling TF32 kernels with mps (torch version 2.9.0) and found the backend sometimes uses silently broken kernels that cause unstable training." — [A1 handout](https://github.com/stanford-cs336/assignment1-basics/blob/main/cs336_assignment1_basics.pdf)

### Inferences
- The most valuable non-generative help is "is this me or the environment?" triage: distinguishing a real implementation bug from float tolerance on Apple Silicon, a library-version drift, or a known handout erratum. An editor that indexes the course repo's CHANGELOG and issues and can say "there is a known tolerance issue on macOS for this exact test" would save hours without touching the solution.
- Passing tests is not proof of correctness in this course (issue #88; bf16 overflow). Students need help generating their own checks (invariants, toy inputs, property tests), which is exactly what AGENTS.md endorses ("Prefer tests and invariants over fixes").
- Memory-safety guard rails matter more on a laptop than on a cluster: pre-run memory estimates and a watchdog that kills a process before macOS locks up would address a repeatedly reported failure.
- Dropout from 30+ to 8 in a study group and "months of evenings" suggest pacing, progress tracking against the 38-problem A1 structure, and visible partial credit are meaningful for self-directed learners.
- Fork/remote setup is a trap for beginners (dozens of accidental upstream PRs); a guided "make this your private repo" step is cheap and useful.

### Gaps
- No Reddit threads or YouTube lecture comments were retrieved; Ed/Slack discussions are private. Pain-point evidence is therefore weighted toward GitHub issues and a handful of blogs.
- I found no first-hand write-up of the 2026 A5 (GRPO with vLLM) from an auditor, and no detailed account of einsum/einops confusion specifically, beyond the handout's own emphasis and the shape-related issues.
- Hyperparameter-sweep and experiment-tracking pain is implied by the assignment structure (sweeps, ablations, learning curves) but I found no direct student complaints about it.

### Inferences
- Literal-cost arithmetic from handout labels at March 2026 B200 rates ($4.99 to $6.25/hr): A1 about 17 GPU-hours is roughly $85 to $106 (only about $35 to $44 without the 10-hour leaderboard budget); A5 about 26 hours is roughly $130 to $163; A4's 16 GPU-hours is roughly $80 to $100. That is above the TA's "$200 liberal" estimate, which implies real self-studiers use cheaper/older GPUs (4090, H100, A100) and scale runs down. These totals are my calculations, not sourced figures.
- The practical auditor pattern is hybrid: edit and unit-test locally on a Mac (CPU), run TinyStories-scale experiments on MPS, and burst to a rented Linux NVIDIA box or Modal for A2, OWT runs and A5. The editor therefore needs a clean local-to-remote story (sync code, launch run, stream metrics, pull checkpoints, stop billing) more than it needs a notebook.
- A cost meter is a real need: runs are labelled in GPU-hours in the handout, cloud GPUs bill by the hour (or second on Modal), and idle instances are the classic way self-studiers overspend.
- Because low-resource tips exist only for A1, an auditor has to invent their own downscaled configs for A2, A4 and A5; helping the student reason about what can be shrunk without invalidating the lesson (the handout's own caution: a debug set must "have the same bottlenecks as the full configuration") is a legitimate coaching task.

- Current (November 2026) GPU prices were not re-checked; the March 2026 site snapshot is the latest course-provided figure.
- No evidence was found on whether Modal's $30/month free credit is enough for any specific assignment.

## 5. Existing tooling for ML debugging and comprehension that an editor could integrate or imitate

### Takeaway
The course already standardizes on uv, pytest with snapshot fixtures, jaxtyping annotations, einops/einx, ruff, the `ty` type checker, wandb, cProfile/py-spy, Nsight Systems, and an IDE debugger; the visible gap students fill themselves is making tensor shapes visible where they read and debug code. Most relevant tools exist as separate libraries or small extensions rather than as one integrated student experience.

### Cited Findings

**What the course itself prescribes**
- Environment and tests: uv (`uv run`, `uv.lock`), pytest with `tests/_snapshots` and `tests/fixtures`, pytest-timeout; lint/type tools ruff and ty are dependencies. — [A1 pyproject.toml](https://github.com/stanford-cs336/assignment1-basics/blob/main/pyproject.toml); [uv docs](https://docs.astral.sh/uv/)

No Python interpreter, JAX installation, or code execution is required"; hovering shows a compact "Shapes" table. — [jaxtypinglint](https://github.com/yubinhu/jaxtypinglint); [assignment5-alignment issue #17](https://github.com/stanford-cs336/assignment5-alignment/issues/17)
- TorchShapeFlow is a VS Code extension doing static shape inference shown on hover without running code (per search summary; not independently evaluated). — [TorchShapeFlow](https://davidxswang.github.io/torchshapeflow/extension/)
- TensorSensor augments exception messages and visualizes the tensor dimensions of the offending sub-expression. — [TensorSensor](https://github.com/parrt/tensor-sensor)

- VS Code's PyTorch support: the variable explorer/data viewer shows tensor shape, and tensors can be opened in a data viewer from the debugger; a debugpy discussion requests showing shape instead of values by default in the debugger. — [VS Code PyTorch support](https://code.visualstudio.com/docs/datascience/pytorch-support); [debugpy discussion #1199](https://github.com/microsoft/debugpy/discussions/1199)

- torchinfo prints a Keras-style per-layer summary with output shapes and parameter counts. — [torchinfo](https://github.com/TylerYep/torchinfo)

**Profiling, tracking, workflows**
- PyTorch's built-in profiler (`torch.profiler`) records CPU/CUDA time and memory per operator and exports traces. — [torch.profiler docs](https://docs.pytorch.org/docs/stable/profiler.html)
- W&B Sweeps automates hyperparameter search; trackio is a lightweight, local-first experiment tracker from the Gradio team with a wandb-like API. — [W&B Sweeps](https://docs.wandb.ai/guides/sweeps/); [trackio](https://github.com/gradio-app/trackio)

- Karpathy's "A Recipe for Training Neural Networks" is the canonical checklist for the sanity checks the handout asks for (overfit one batch, verify loss at init, inspect data). — [karpathy.github.io recipe](https://karpathy.github.io/2019/04/25/recipe/)
- CS336's own lectures use an executable-trace format: `lecture_XX.py` compiled by `execute.py` into a JSON trace and viewed in the `edtrace` frontend, so learners step through real code with values. — [stanford-cs336/lectures README](https://github.com/stanford-cs336/lectures)

### Inferences
- Highest-leverage integrations for this user, in my judgment: (1) jaxtyping-aware hovers and inline shape display, both static (from annotations) and live (from the last debug/test run); (2) a pytest explorer that understands the `adapters.py` indirection, maps each test to its handout problem, and renders snapshot diffs as numeric summaries (max abs/rel error, fraction mismatched, likely-tolerance vs likely-bug); (3) one-click cProfile/py-spy/torch.profiler flame graphs; (4) run tracking with wall-clock x-axes and GPU-hour accounting; (5) remote run management over SSH/Modal.
- Scripts, not notebooks, are the course's native form (`uv run script.py`, packages, pytest), so `# %%`-style scratch cells or a REPL attached to the package fit better than a notebook-first design.
- Gradient checking (`torch.autograd.gradcheck`) is directly relevant to A2's hand-written FlashAttention backward pass and custom autograd Functions, but I did not verify a documentation URL for it in this session (the URL I tried returned 404), so it is not cited above. The same applies to PyTorch named tensors.
- The existence of three separate small extensions for shape display, one built by a CS336 learner this month, is evidence of unmet demand rather than a solved problem.

### Gaps
- I did not evaluate the maturity or current maintenance of TorchShapeFlow, DebugTShow, TensorSensor or lovely-tensors; they are cited as existing approaches only.
- No source was found on which editors CS336 students actually use (the handout names VS Code and Zed as examples) or on notebook-vs-script preferences among self-studiers.
- PyTorch named tensors and `gradcheck` documentation links were not verified.

## 6. Reference-material workflows: lectures, handouts, papers

### Takeaway
The course's reference set is self-contained by design: long handout PDFs with numbered sections and named problems, a public YouTube playlist, executable-lecture traces and slide PDFs, and the papers the handouts cite. Students cross-reference these manually; I found no tool that links code to handout sections, paper sections or lecture timestamps, apart from the course's own executable-lecture viewer.

### Cited Findings
- The handouts are the primary spec: A1 is 47 pages, A2 48, A5 39, A4 16, A3 8, each organized as numbered sections with "Problem (name): title (points)" boxes and "Deliverable:" lines; adapters and tests are named after the problems (e.g. `adapters.run_save_checkpoint`, `uv run pytest -k test_checkpointing`). — [A1 handout](https://github.com/stanford-cs336/assignment1-basics/blob/main/cs336_assignment1_basics.pdf)
- "The handouts we'll give will be self-contained, so that you will not need to consult third-party code"; AGENTS.md tells agents to "Point students to relevant lecture materials (cs336.stanford.edu), handouts, official documentation" and not to "Point students to third-party implementations." — [cs336.stanford.edu](https://cs336.stanford.edu/); [CLAUDE.md](https://github.com/stanford-cs336/assignment1-basics/blob/main/CLAUDE.md)
- Handouts change during the quarter (A1 went 26.0.0 to 26.0.3 in eight days, including a fixed SGD example and a changed leaderboard limit; 2025 had six point releases including three RoPE formula fixes), tracked in CHANGELOG.md, with students told to `git pull`. — [A1 CHANGELOG](https://github.com/stanford-cs336/assignment1-basics/blob/main/CHANGELOG.md)
- Lectures: 19 sessions in 2026; the site links a single YouTube playlist rather than per-lecture videos, plus per-lecture materials (`lecture_XX.py` traces at `cs336.stanford.edu/lectures/?trace=lecture_01` or PDFs in the lectures repo). Lecture topics align with assignments (e.g. lecture 2 "PyTorch (einops), resource accounting", lecture 6 "Kernels, Triton", lectures 7 to 8 "Parallelism", 9 and 11 "Scaling laws", 13 to 14 data, 15 to 16 post-training/RLVR). — [cs336.stanford.edu](https://cs336.stanford.edu/); [stanford-cs336/lectures](https://github.com/stanford-cs336/lectures)
- Handout-linked references in A1 include the einops and einx tutorials, jaxtyping, PyTorch MPS notes, a tiktoken PR, modded-nanogpt, and cited papers (BPE: Sennrich et al. 2016; TinyStories: Eldan et al. 2023; AdamW; Kaplan et al. and Hoffmann et al. for scaling). — [A1 handout](https://github.com/stanford-cs336/assignment1-basics/blob/main/cs336_assignment1_basics.pdf)
- Auditor advice on lectures: do not rush; spend up to about 2.5x lecture length pausing, rewinding and chasing references; references from Tatsu's lectures were among the most useful takeaways; the same auditor used Claude "for questions about lectures". — [Andy Timm review](https://andytimm.github.io/posts/cs336/cs336_review.html)
- Community members publish lecture notes per lecture (e.g. a "CS336 Lecture 1 - Overview and Tokenization" note series and a combined lecture-notes-and-assignments site), indicating note-taking alongside the videos is a common practice. — [tuananhbui89 lecture notes](https://tuananhbui89.github.io/blog/2025/cs336-lec01); [yyzhang2025 notes](https://yyzhang2025.github.io/LearningNotes/posts/CS336/index.html)
- Paper/spec divergence is itself a source of confusion: issue "AdamW Optimizer formula in Section 4.3 differs from original" led to the 26.0.0 fix "Fix AdamW disparity to paper (order of weight-decay vs gradient update)". — [issue #54](https://github.com/stanford-cs336/assignment1-basics/issues/54); [A1 CHANGELOG](https://github.com/stanford-cs336/assignment1-basics/blob/main/CHANGELOG.md)

### Inferences
- The natural anchor for linking is the handout's problem name: it already ties together a PDF section, an adapter function, one or more tests, and a writeup answer. An editor could build a "problem card" from these with no AI at all, then attach the relevant lecture and paper pointers.
- Since AGENTS.md wants answers grounded in course materials, an assistant with retrieval over the handout PDF, lecture traces/slides, and the cited papers, answering with section and equation references ("see handout section 3.5.3, equation 11"), is both more policy-compliant and more useful than free-form explanation.
- Version awareness matters: an explanation should be grounded in the student's checked-out handout version, and the editor should surface CHANGELOG entries that touch the section the student is working on (the RoPE and AdamW errata are the concrete cases).
- Lecture-timestamp linking would require transcripts of the YouTube playlist; nothing found suggests anyone has built this for CS336.

- I did not verify whether the 2026 lecture videos have public transcripts or chapter markers, or how many of the 19 lectures are on the playlist.
- No direct student accounts of how they arrange PDF/video/code on screen.

## 7. Which kinds of AI help fit the course's intent and which defeat it

### Takeaway
The course itself now draws the line in writing: AI may explain concepts, look up APIs and documentation, explain error messages, ask guiding questions, suggest sanity checks/invariants/profiling investigations, and review student-written code in general terms; it may not write Python or pseudocode, edit the repo, run commands, complete TODOs, hand over the bug or the idea, or point to third-party implementations. Self-studiers who report good outcomes adopted essentially this stance voluntarily.

### Cited Findings
- Permitted, per the policy doc: "answering high-level conceptual questions or... providing low-level programming documentation like function signatures and library APIs". Prohibited: "implementing any part of any assignment", including via "coding agents" and "AI autocomplete"; "It is not okay to ask LLMs or coding agents to write any code." — [CS336 AI Policy doc](https://docs.google.com/document/d/1SZAlExB1qAc9izHt54gwunNpjKE6wXb8Y7yA_e-baK8/edit?tab=t.0)
- Non-AI assistance is explicitly fine: "non-AI autocomplete, e.g., autocompleting function names, is permitted". — [CS336 AI Policy doc](https://docs.google.com/document/d/1SZAlExB1qAc9izHt54gwunNpjKE6wXb8Y7yA_e-baK8/edit?tab=t.0)
- Endorsed behaviours in AGENTS.md: explain concepts; point to lectures/handouts/docs/profiling tools; review student code and "suggest improvements, edge cases, invariants, or debugging checks" in general terms; "Help debug by asking guiding questions rather than providing fixes"; "Explain error messages from Python, PyTorch, CUDA, Triton, and distributed training tools"; "Suggest sanity checks, toy examples, assertions, and profiler-based investigations through active dialog". — [CLAUDE.md](https://github.com/stanford-cs336/assignment1-basics/blob/main/CLAUDE.md)
- Forbidden behaviours in AGENTS.md include some that go beyond code generation: "Write any python or pseudocode", "Edit code in the student repo", "Run bash commands", "Point students to third-party implementations", "Give the student the solution or idea for how to solve a problem". The fallback when a request crosses the line is "explanation, debugging guidance, code review, or a non-pasteable high-level outline." — [CLAUDE.md](https://github.com/stanford-cs336/assignment1-basics/blob/main/CLAUDE.md)
- Rationale given by staff: "AI can solve many parts of the assignments fully autonomously. This makes it harder to deeply engage with, and learn from, the course material" and "Previous students have highlighted that disabling AI autocomplete made it easier to engage deeply with the material." — [A1 handout](https://github.com/stanford-cs336/assignment1-basics/blob/main/cs336_assignment1_basics.pdf)
- The office-hours test: "ask yourself whether a CA would comply with your request in office hours." — [CS336 AI Policy doc](https://docs.google.com/document/d/1SZAlExB1qAc9izHt54gwunNpjKE6wXb8Y7yA_e-baK8/edit?tab=t.0)
- Leaderboards: "Any use of AI or external code copying will result in a disqualification." — [assignment1-basics-leaderboard README](https://github.com/stanford-cs336/assignment1-basics-leaderboard)
- Self-studier practice 1: an auditor "wrote down clear rules for what Claude could help with and encoded them in a `CLAUDE.md` file so that asking for a hint would not produce a full solution", used Claude for lecture questions and for side projects where that felt acceptable, and advises deciding early how much LLM assistance you want and documenting it, warning against erring too far in either direction (per fetch summary of the post). — [Andy Timm review](https://andytimm.github.io/posts/cs336/cs336_review.html)
- Self-studier practice 2: "forced myself to write code without using AI" and used Claude as a "TA for high level programming related questions." — [dotvignesh Substack](https://dotvignesh.substack.com/p/building-a-byte-pair-encoding-tokenizer)
- Counter-examples exist in public: an upstream PR titled "AI optimized BPE trainer and tokenizer", and a CSDN post whose author says ChatGPT wrote nearly all the code (per search summary). — [assignment1-basics PR #20](https://github.com/stanford-cs336/assignment1-basics/pull/20); [CSDN post](https://modelers.csdn.net/69a7804d7bbde9200b9ce70e.html)
- Other courses' line is "substantial completion": CS224N allows AI "as collaborators in the problem-solving process" but not "to substantially complete assignments"; CS231N requires writing solutions "independently of the output of the interaction" plus a note describing the collaboration; CMU Deep Learning Systems allows AI coding assistance with no citation but recommends doing HW0 unaided "to ensure foundational understanding". — [CS224N](https://web.stanford.edu/class/cs224n/); [CS231N assignments](https://cs231n.stanford.edu/assignments.html); [dlsyscourse.org](https://dlsyscourse.org/)

### Inferences
Classification of assistance types against the CS336 2026 texts (my mapping; each row follows from the cited lists above):
- Clearly consistent: concept explanation grounded in handout/lecture/paper; API and signature lookup (PyTorch, einops, Triton, NCCL, vLLM); explaining stack traces and CUDA/Triton errors; Socratic debugging ("what did you expect, what happened?"); proposing sanity checks, toy inputs, shape assertions and invariants in prose; helping interpret profiler output and loss curves; general-terms review of code the student already wrote; quizzing and "explain it back" checks; environment/setup triage (uv, CUDA versions, platform limits), since that is not an assignment problem. Quizzing is not named in AGENTS.md but passes the office-hours test.
- Grey zone that needs careful design: naming a specific bug location (AGENTS.md wants "likely bugs" surfaced "through dialog rather than directly giving them"); high-level algorithm outlines (allowed only if "non-pasteable"; pseudocode is banned); suggesting a specific optimization idea for BPE or FlashAttention (banned as giving "the solution or idea"); writing test code for the student (it is Python, so banned as written, though the intent "Prefer tests and invariants" suggests describing the test instead); generating plotting or sweep boilerplate (the policy says "All experiments you run should be written by you").
- Clearly defeats the course: AI autocomplete of any implementation code; agent edits to the repo; filling adapters or TODOs; converting handout text to code; refactoring student code into a working solution; pointing to nanoGPT/minbpe-style reference implementations; running commands on the student's behalf.
- Product implications: (1) default to no inline AI completion while keeping language-server completion; (2) the assistant should have read access to code, tests, run outputs and course materials but no write or execute capability; (3) answers should be prose with references rather than code blocks, with a hard block on emitting assignment-relevant code; (4) a visible, user-set "policy level" that reads `AGENTS.md`/`CLAUDE.md` when present; (5) since an auditor has no TA, the assistant substitutes for office hours, and the office-hours test is the right behavioural spec; (6) an auditor may legitimately want looser rules for non-assignment side projects (as the Andy Timm review describes), so policy should be scoped per workspace, not global.
- A self-directed learner has no external enforcement, so the tool's role is to make the committed behaviour the easy path (and make exceptions deliberate and logged), not to police.

### Gaps
- No empirical evidence was found (in CS336 or the comparable courses) measuring learning outcomes under different AI-assistance modes; the staff's rationale is anecdotal ("Previous students have highlighted...").
- I found no staff statement on how auditors should apply the policy, beyond the leaderboard rule for external submissions.
- How well current coding agents actually comply with the CS336 AGENTS.md in practice (e.g., refusing to write code when pressed) was not tested or documented in any source found.
